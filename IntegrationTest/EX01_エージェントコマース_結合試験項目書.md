# EX01_エージェントコマース_結合試験項目書

EX は画面を持たない機能（API・CLI）の結合試験項目です。

### 事前準備

対象は EC-CUBE 4.4 のエージェントコマース（ACP: Agentic Commerce Protocol / UCP: Universal Commerce Protocol）と MCP（Model Context Protocol）サーバ。本項目書の API 項目は curl 等の HTTP クライアントから直接エンドポイントを叩いて確認する。管理画面の設定と運用画面の項目は EA15 にある。

1. プラグイン
   1. API プラグイン（eccube-api4）の 4.4 ブランチ（https://github.com/EC-CUBE/eccube-api4/tree/4.4）をインストールし有効化する。ACP チェックアウトの OAuth2 Bearer 認証と MCP サーバの認証に必要（4.4.0-alpha-1 リリースノートの前提条件）。UCP チェックアウト・Discovery・カタログは API プラグイン無しでも動作する
   2. EX0107 のみ、決済ハンドラを提供する sample-payment-plugin の 4.4 ブランチ（https://github.com/EC-CUBE/sample-payment-plugin/tree/4.4）が追加で必要。sample-payment-plugin を導入して配送方法に sample 決済を許可すると、create 時にその支払方法が割り当てられ、ボディ `{}` の complete も決済ハンドラ経由になってトークン無しで失敗する。EX0103 / EX0104 はプラグイン未導入の状態で実施し、EX0107 は最後に実施する
2. HTTPS
   1. 4.4 はセッション Cookie に `SameSite=None` を付与するため、HTTP で動かすと管理画面にログインできない。`symfony server:start` 等の HTTPS 環境で確認する（HTTP で確認する場合は `app/config/eccube/packages/framework.yaml` の `cookie_samesite: none` を `lax` に変更し `var/cache` と `var/build` を削除する）
   2. 以降のリクエスト例は `https://example.com` を店舗 URL に、`admin` を管理画面 URL（`eccube_admin_route`）に読み替える
3. 店舗設定のフラグ（いずれも初期値は無効）
   1. 設定＞店舗設定＞基本設定の「エージェントコマース」で ACP / UCP チェックアウト、「MCP サーバ」で MCP を切り替える
   2. SQL で `dtb_base_info` を直接更新した場合は `bin/console cache:pool:clear --all` を実行する（BaseInfo はキャッシュされるため、更新が反映されず 404 のままになる）
4. 環境変数（`.env`）
   1. `ECCUBE_AGENT_COMMERCE_UCP_SIGNING_KEY`: UCP 署名鍵ファイルのパス上書き（未設定なら `app/keystore/agent-commerce/ucp_signing.key`）
   2. `ECCUBE_AGENT_COMMERCE_ACP_WEBHOOK_SECRET`: ACP Webhook 共有シークレットのパス上書き（未設定なら `app/keystore/agent-commerce/acp_webhook.key`）
   3. `ECCUBE_AGENT_COMMERCE_ACP_FEED_BASE_URL` / `ECCUBE_AGENT_COMMERCE_ACP_FEED_API_KEY`: ACP プロダクトフィード push 先と Bearer キー。両方設定されるまで push は失敗する
   4. `ECCUBE_KEYSTORE_STRICT_PERMISSIONS`: `1` で鍵を 0700 / 0600 で作成する（既定は 0755 / 0644）
   5. `ECCUBE_MCP_ALLOWED_ORIGINS`: MCP の Origin 許可リスト（カンマ区切り）。未設定時、`APP_DEBUG=0`（`kernel.debug` が false）では Origin ヘッダ付きリクエストを拒否し、`APP_DEBUG=1` では検証しない（`APP_ENV` ではなく `kernel.debug` で決まる）
   6. `ECCUBE_MCP_LOG_RETENTION_DAYS`: MCP 監査ログの保持世代数（既定 90）
   7. `eccube_agent_checkout_escalation_expire`（`app/config/eccube/packages/eccube.yaml`、既定 15 分）: 追加認証待ちの在庫確保期限
5. テストデータ
   1. 公開中の商品に在庫数管理（在庫無制限 OFF）の規格を作り、`dtb_product_class.id`（以下 `<PRODUCT_CLASS_ID>`）を控える。`visible = 0` の規格は購入明細から除外されるため使わない
   2. 在庫 0 の規格を用意する（在庫切れの確認用、`<OUT_OF_STOCK_CLASS_ID>`）
   3. 在庫 1 の規格を ACP 用（`<LOW_STOCK_CLASS_ID_ACP>`）と UCP 用（`<LOW_STOCK_CLASS_ID_UCP>`）に 1 つずつ用意する（在庫数を超える数量の切り詰めの確認用）。切り詰めの項目は complete まで進めて在庫が 0 になるため、ACP と UCP で同じ規格を使わない。shopping フローの在庫チェック（`StockMultipleValidator`）は、在庫数を超える数量を在庫数まで切り詰めて warning を返す（error にはならない）
   4. 配送方法・支払方法は標準のまま（決済ハンドラプラグイン未導入の状態では complete は与信なしで受注確定する）
6. ACP 用 OAuth2 トークン（API プラグインが提供）
   1. クライアント作成: `bin/console league:oauth2-server:create-client --grant-type=client_credentials --scope=acp:checkout --scope=ucp:checkout agentTest YOUR_CLIENT_ID YOUR_CLIENT_SECRET`
   2. トークン発行: `curl -s -X POST https://example.com/token -d grant_type=client_credentials -d client_id=YOUR_CLIENT_ID -d client_secret=YOUR_CLIENT_SECRET --data-urlencode 'scope=acp:checkout'` の `access_token` を `YOUR_ACCESS_TOKEN` とする
   3. scope 不足の確認用に `--scope=ucp:checkout` のみのクライアントも作り、そのトークンを `YOUR_UCP_ONLY_TOKEN` とする
7. MCP 用トークン（API プラグインが提供）
   1. 権限が「システム管理者」のメンバーで管理画面にログインし、`https://example.com/admin/api/oauth/mcp/new` でラベル、scope（`mcp:product:read` / `mcp:order:read` / `mcp:customer:read` / `mcp:plugin:read`）、有効期限（30日 / 90日 / 180日）を選んで発行する。システム管理者以外の権限では発行時に 403 になる。トークンは発行直後の画面にのみ表示される
   2. 4 scope すべてを持つトークンを `YOUR_MCP_TOKEN`、`mcp:product:read` のみのトークンを `YOUR_MCP_PRODUCT_TOKEN` とする
8. ACP / UCP の冪等キー（`Idempotency-Key` ヘッダ）はリクエストごとに新しい値（例: `uuidgen`）を使う。冪等キーは (キー, 認証主体) ごとに path・method・ボディのハッシュと応答を保存するため、同じ値を別のリクエストに使うと conflict（ACP 422 / UCP 409）、同じリクエストに使うと前回応答のリプレイになる。同じ値を再利用する手順は明記する

  -H 'Authorization: Bearer YOUR_ACCESS_TOKEN' \

## EX0101-UC01-T01_UCP_discoveryの応答

1. `curl -s -D - https://example.com/.well-known/ucp` を実行する
2. 200、`Content-Type: application/json`、`Cache-Control: public, max-age=300`（`private` / `no-store` / `no-cache` を含まない）、リダイレクトでないことを確認する
3. ボディが以下を満たすことを確認する
   1. `ucp.version` が `2026-04-08`
   2. `ucp.services["dev.ucp.shopping.catalog"]` が配列で、先頭要素に `transport: "rest"` と絶対 URL の `endpoint`（`https://example.com/catalog`）を持つ
   3. `ucp.capabilities["dev.ucp.shopping.catalog.search"]` と `["dev.ucp.shopping.catalog.lookup"]` が配列で、各要素に `version` と `schema` を持つ
   4. `ucp.payment_handlers` が `{}`（決済ハンドラプラグイン未導入時。`[]` ではない）
   5. `signing_keys` が配列で、各要素が `kty: "EC"`、`crv: "P-256"`、`kid`、`x`、`y` を持ち、`d` / `p` / `q` / `dp` / `dq` / `qi` / `k` を含まない
4. 鍵ファイル `app/keystore/agent-commerce/ucp_signing.key` が無い状態で初回アクセスした場合は、アクセス後に自動生成されていることを確認する

## EX0102-UC01-T01_UCPカタログ_search

1. `curl -s -X POST https://example.com/catalog/search -H 'Content-Type: application/json' -d '{}'` を実行する
2. 200、`Content-Type: application/json` で、ボディが以下を満たすことを確認する
   1. `ucp.version` が `2026-04-08`、`ucp.status` が `success`
   2. `products` が公開商品の配列で、各要素が `id`（商品 ID）、`title`、`description`、`price_range.min/max`（`amount` 整数、`currency`）、`variants`、`url`（商品詳細の絶対 URL）を持つ
   3. 商品画像がある商品は `media[]` に `type: "image"` と絶対 URL の `url` を持つ
   4. 各 `variants[]` が `id`（規格 ID）、`title`、`price.amount`（税込価格の整数）、`price.currency`、`availability.available`、`availability.status` を持ち、商品コードがあれば `sku`、規格があれば `options[]`（`name` / `label`）を持つ
   5. `messages` が `[]`、`pagination.has_next_page` が真偽値
3. 空ボディ（`-d ''`）でも同じ応答になることを確認する

## EX0102-UC01-T04_UCPカタログ_非公開商品と非表示規格の除外

1. 公開中の商品 A を search / `{"ids": ["<Aの商品ID>"]}` の lookup / `{"id": "<Aの商品ID>"}` の product で取得できることを確認する

5. 商品 A を公開に戻し、規格の 1 つを非表示にすると、その規格だけが `variants[]` から消えることを確認する
6. 全規格を非表示にすると、商品 A 自体が search から消えることを確認する

## EX0102-UC01-T05_UCPカタログ_在庫状況の出力

3. 在庫数管理で在庫 0 の規格: `available` が `false`、`status` が `out_of_stock` であることを確認する
4. 通常価格（price01）が販売価格（price02）より高い規格: `list_price.amount` に税込の通常価格が出力されることを確認する
5. 通常価格が販売価格以下、または未設定の規格: `list_price` が出力されないことを確認する

## EX0102-UC01-T06_UCPカタログ_lookup

1. `curl -s -X POST https://example.com/catalog/lookup -H 'Content-Type: application/json' -d '{"ids": ["<商品ID>"]}'` を実行し、200 で `products` に該当商品 1 件が返ることを確認する
2. `{"ids": ["<商品ID>", "<商品ID>"]}` のように同じ ID を重複指定しても 1 件に集約されることを確認する
3. `{"ids": ["<規格ID>"]}` のように規格 ID を指定しても親商品が返ることを確認する。数字だけの ID は商品 ID として先に解決されるため、どの商品 ID とも重ならない規格 ID を使う
4. `{"ids": ["<商品コード>"]}` のように規格の商品コード（SKU）を指定しても親商品が返ることを確認する。数字だけの商品コードは商品 ID・規格 ID として解決されるため、数字以外を含む商品コードを使う
5. `{"ids": ["99999999"]}` で 200 かつ `products` が `[]` であることを確認する（エラーにならない）

## EX0102-UC01-T12_ACPプロダクトフィード_実送出（手動確認）

※OpenAI がホストする ACP Feed API の認証情報が必要なため、外部サービスを使う手動確認項目とする。

1. `ECCUBE_AGENT_COMMERCE_ACP_FEED_BASE_URL` と `ECCUBE_AGENT_COMMERCE_ACP_FEED_API_KEY` を設定する
2. コンテンツ管理＞エージェントコマースでフィード ID を入力し「全置換 push」を押し、「全置換 push を送信しました (N 件)。」（N は公開商品数）が表示されることを確認する
